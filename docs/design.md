# 公募基金策略监控工具：产品策划案与 AI 独立开发计划

## 1. 产品定位与核心价值主张：用自动化规则引擎接管 30+ 只基金的每日盯盘

面对个人同时持有 20 至 50 只公募基金的分散配置场景，传统基金交易平台（如支付宝、天天基金、且慢等）普遍只提供简单的“目标止盈”或“定投提醒”，缺乏针对**动态最高点回撤（移动止盈）**、**分档止损**以及**基金自身业绩与历史最大回撤联动**的复合规则引擎。投资者往往因无法每日逐一复盘 30 多只基金的净值变化，错过预设的纪律性执行节点。

本产品定位为一款**轻量级、跨平台的公募基金量化策略监控与客观指标提醒工具**，遵循“先满足个人深度自用，再平滑演进为面向公众开放的合规效率小工具”的迭代路径：

| 核心维度 | 规划方案与设计边界 |
| :--- | :--- |
| **核心痛点解决** | 解决多基金持仓（30+ 只）难以人工盯盘、缺乏“最高盈利回撤 $X\%$ 触发提醒”及“个人持仓表现与基金自身历史回撤分离监控”的痛点 |
| **净值数据基准** | 摒弃失真率较高的盘中实时估算，严格采用每晚官方披露的**实际单位净值、累计净值与复权净值**进行盘后精确核算与提醒 |
| **持仓录入与维护** | 仅识别截图上明确带有**成本价、持仓份额/金额、盈亏**等完整信息的平台截图（信息不全直接提示识别不到有效信息，不做复杂反推托底）；入库后每日按最新官方净值**自动刷新市值、盈亏与最高水位线** |
| **合规边界设计** | 定性为“客观数据统计与自定义阈值通知工具”，通知文案只陈述客观指标触发状态与用户自设标签，不输出“建议清仓/减仓”等投顾指令 |
| **零成本免服务器部署** | 采用 **[Vercel](https://www.google.com/search?q=https%3A%2F%2Fvercel.com%2F)（前端与 API） + [Supabase](https://www.google.com/search?q=https%3A%2F%2Fsupabase.com%2F)（免费云端 Postgres 数据库） + [GitHub Actions](https://www.google.com/search?q=https%3A%2F%2Fdocs.github.com%2Factions)（每晚定时抓取与计算）** 全免费 Serverless 架构，无需购买云服务器即可实现 24 小时无人值守推送与手机 5G 外网随时访问 |
| **终端形态演进** | 第一阶段采用 **响应式 Web + PWA（渐进式网页应用）** 极速上线自用；第二阶段通过 [uni-app](https://www.google.com/search?q=https%3A%2F%2Funiapp.dcloud.net.cn%2F) 扩展至 **微信小程序 + 微信服务号通知** 开放公测 |

## 2. 核心业务架构与精确计算口径：分离个人持仓盈亏与基金客观业绩

为了彻底区分“我在这只基金上赚/亏了多少”与“这只基金本身近期走势及历史风险处于什么位置”，系统在底层数据模型上将监控逻辑拆分为**个人持仓轨道**与**基金客观业绩轨道**。

### 2.1 数据采集引擎：基于盘后官方净值与复权因子的定时同步

公募基金涉及现金分红与份额拆分。如果仅使用“单位净值（Unit NAV）”计算基金自身涨幅或历史最大回撤，遇到大额分红当日会出现虚假的“暴跌缺口”。因此系统必须同时维护两套净值口径：

1. **个人持仓核算口径（使用单位净值 $NAV_t$）**：用户实际持有的基金份额乘以当日官方单位净值，即为当前真实持仓市值。
2. **基金自身业绩与历史回撤口径（使用复权单位净值 $AdjNAV_t$）**：考虑分红再投资假设下的真实业绩曲线，用于计算基金阶段涨跌幅、区间回撤与历史最大回撤。

数据源获取方面，通过 [GitHub Actions](https://www.google.com/search?q=https%3A%2F%2Fdocs.github.com%2Factions) 定时运行 Python 脚本，调用开源财经数据接口库 [AKShare](https://www.google.com/search?q=https%3A%2F%2Fgithub.com%2Fakfamily%2Fakshare) 及 [天天基金网](https://www.google.com/search?q=https%3A%2F%2Ffund.eastmoney.com%2Fdefault.html) 静态 CDN 接口（`pingzhongdata/{code}.js`）拉取数据，并以新浪财经基金接口作为海外节点备用源：

| 基金类型 | 官方净值披露窗口 | GitHub Actions 定时同步策略（错峰双次扫描） | 核心采集字段 |
| :--- | :--- | :--- | :--- |
| **普通开放式基金（股票/混合/债券型）** | 交易日 19:30 – 22:00 | 交易日北京时间 **21:17**（主力扫描）与 **22:47**（晚点净值补抓）分两次运行，按 `last_evaluated_nav_date` 幂等去重 | 基金代码、净值日期、单位净值、累计净值、日增长率、当日分红配送信息、复权净值序列 |
| **FOF 基金与部分债券基金** | 交易日 22:00 – 次日 08:30 | 次日北京时间 **08:47** 补抓前一交易日尚未更新净值的标的 | 基金代码、最新确认净值日期、单位净值、复权净值 |
| **QDII 跨境基金** | $T+1$ 日晚间或 $T+2$ 日晨间 | 随每日 **08:47** 晨间任务一并扫描前两个交易日尚未更新净值的 QDII 标的并触发策略重算 | 基金代码、对应海外交易日净值、折算后净值 |

### 2.2 截图智能识别（OCR + 多模态提取）与持仓自动刷新机制

由于国内主流代销平台不向个人开发者开放持仓查询 API，采用**“标准截图直读录入 + 缺失字段快速报错拦截 + 每日按净值自动刷新”**是开发最简单、数据最准确的闭环方案。

#### （1）多模态截图直读链路
用户在前端上传带有完整持仓明细的平台截图（如天天基金、东方财富、支付宝单只基金持仓详情页或带有成本单价的持仓表），前端自动将图片压缩至宽度 $\le 1280\text{px}$ 后按单张并发请求后端接口，直接调用多模态大模型 Vision API（如通义千问 `Qwen-VL-Plus` 或 Gemini Flash Vision）读取明确可见的文字与数字并输出结构化 JSON。

#### （2）严格字段校验与“快速失败（Fail-Fast）”原则（不做复杂托底反推）
为了大幅降低开发复杂度并杜绝跨日净值反推带来的计算误差，系统对截图识别采取**“所见即所得，缺项直接报错”**的严格准入逻辑：

* **明确要求识别的核心字段**：
  1. **基金标识**：基金 6 位代码 `fund_code`（或完整标准基金名称 `fund_name`）；
  2. **持仓成本价**：截图上明确显示的持仓成本单价 `cost_unit`；
  3. **持仓规模与盈亏**：截图上明确显示的持有份额 `shares`（或持有金额 `market_value` / 持仓成本总额 `total_cost`）以及持有盈亏金额 `profit` / 持有收益率 `return_pct`。
* **信息不全时的拦截反馈**：
  若用户上传的截图不包含上述明确字段（例如截成了没有成本价的简版列表页、图片裁切不全或关键数字模糊），后端**不做任何复杂的间接托底推算**，直接向前端返回校验失败状态与明确提示：
  > `“未识别到完整的有效持仓信息（缺少成本价、持仓份额或盈亏明细），请上传带有完整持仓明细的页面截图，或直接在输入框中手动补全。”`
* **持仓期最高水位线（High-Water Mark, HWM）初始化与历史回溯**：
  由於老持仓在首次截图录入时，截图上只显示“当前净值”而不显示“过去几个月你持有期间曾经达到过的最高净值”，系统在导入确认弹窗提供**“建仓大致日期 / 回溯天数（如回溯近 60 日最高净值）”**选项：
  1. 若用户指定了建仓日期或回溯窗口 $W_{init}$，系统自动取该区间内的最高官方单位净值 $\max_{\tau \in W_{init}}(NAV_\tau)$ 作为初始最高水位线 $HWM_{nav}$；
  2. 若为新近建仓，则默认以当前净值 $NAV_0$（当 $NAV_0 > Cost_{unit}$ 时）或用户手动输入的最高净值作为初始 $HWM_{nav}$。

#### （3）每日净值更新后的全自动刷新公式
一旦截图中的持仓成本单价 $Cost_{unit}$、持有份额 $S$ 和最高水位线 $HWM_{nav}$ 写入 [Supabase](https://www.google.com/search?q=https%3A%2F%2Fsupabase.com%2F) 数据库，后续每个交易日 $t$ 晚间获取最新官方单位净值 $NAV_t$ 后，系统自动执行以下刷新计算：

* **当日最新持仓市值**：
  $$M_t = S \times NAV_t$$
* **当日累计持仓盈亏金额**：
  $$P_t = S \times (NAV_t - Cost_{unit})$$
* **当日累计持仓收益率**：
  $$R_t = \frac{NAV_t - Cost_{unit}}{Cost_{unit}} \times 100\%$$
* **动态最高水位线自动上移（仅当创出新高时更新）**：
  $$HWM_{nav}(t) = \max\left(HWM_{nav}(t-1),\ NAV_t\right)$$
  $$HWM_{return}(t) = \frac{HWM_{nav}(t) - Cost_{unit}}{Cost_{unit}} \times 100\%$$

### 2.3 双轨监控策略规则引擎（7 大核心监控模型）

系统支持为全部 30+ 只基金设置**全局默认策略模板**（一键应用到所有持仓），支持针对单只基金单独覆盖参数，并支持**账户总资产组合级回撤监控**。

#### 轨道一：基于用户个人持仓盈亏的监控规则

由于股民和基民在表达“盈利以后回撤 5%”时通常存在两种计算习惯——**口径 A（最高净值/市值相对回撤比例）**与**口径 B（最高收益率绝对回落百分点）**，系统在策略配置页提供明确的单选开关，消除歧义：

| 策略类型 | 适用场景 | 触发条件数学表达式 | 算例说明（假设成本 $1.0000$，曾涨至最高净值 $1.2000$ 即最高盈利 $+20\%$） |
| :--- | :--- | :--- | :--- |
| **1A. 移动止盈（按最高市值/净值相对回撤比）** | 保护整体资产（本金+浮盈）不缩水超过 $X\%$ | 满足激活门槛 $HWM_{return}(t) \ge M\%$，且：<br>$$DD_{pos\_nav}(t) = \frac{HWM_{nav}(t) - NAV_t}{HWM_{nav}(t)} \ge X\%$$ | 设盈利满 $5\%$ 激活、高点回撤阈值 $X=5\%$：当净值从最高点 $1.2000$ 下跌 $5\%$ 至 $1.1400$（此时盈利仍为 $+14\%$）时触发提醒 |
| **1B. 移动止盈（按最高收益率回落百分点）** | 锁定已获浮盈百分点，从最高收益率回吐 $X\%$ 触发 | 满足激活门槛 $HWM_{return}(t) \ge M\%$，且：<br>$$DD_{pos\_ret}(t) = HWM_{return}(t) - R_t \ge X\%$$ | 设最高收益率为 $+20\%$、回撤阈值 $X=5\%$：当累计收益率从 $+20\%$ 回落 $5$ 个百分点至 $+15\%$（即净值跌至 $1.1500$）时触发提醒 |
| **1C. 移动止盈（按纯浮盈金额回吐比例）** | 针对小幅盈利阶段，防止利润回吐殆尽变亏损 | 满足 $HWM_{nav}(t) > Cost_{unit}$，且：<br>$$DD_{profit}(t) = \frac{HWM_{nav}(t) - NAV_t}{HWM_{nav}(t) - Cost_{unit}} \ge X\%$$ | 设最高浮盈为 $2000$ 元、利润回吐阈值 $X=30\%$：当浮盈缩水 $30\%$ 降至 $1400$ 元时触发提醒 |
| **2. 目标止盈（固定收益率/金额阶梯提醒）** | 达到心理预期收益目标时的分批止盈提醒 | $$R_t \ge Y\% \quad \text{或} \quad P_t \ge Z\text{ 元}$$ | 设目标止盈率 $Y=15\%$：当持仓累计收益率首次达到或突破 $+15\%$ 时触发提醒 |
| **3. 严格止损（持仓亏损比例/金额提醒）** | 建仓后走势不及预期，触及最大容忍亏损底线 | $$R_t \le -K\% \quad \text{或} \quad P_t \le -L\text{ 元}$$ | 设止损线 $K=5\%$：当持仓收益率跌至 $-5.00\%$ 及以下（净值 $\le 0.9500$）时立即触发止损预警 |
| **4. 账户总组合高点回撤监控** | 防范 30 只基金同板块共振下跌导致的整体资产大幅缩水 | 记 30 只基金合计最高总市值为 $HWM_{portfolio}$：<br>$$\frac{HWM_{portfolio} - \sum M_t}{HWM_{portfolio}} \ge G\%$$ | 设组合整体回撤线 $G=3\%$：当 30 只基金合计总市值较历史最高点回撤满 $3\%$ 时触发全局仓位预警 |

#### 轨道二：基于基金自身客观业绩与历史回撤的监控规则（支持持仓基金与自选观察池基金）

无论用户当前是否持有该基金，或者用户因高位补仓导致个人持仓成本失真，轨道二均直接基于基金自身的**复权单位净值（$AdjNAV_t$）**进行独立监控：

| 策略类型 | 适用场景 | 触发条件数学表达式 | 业务价值与实战用途 |
| :--- | :--- | :--- | :--- |
| **5. 基金阶段高点回撤监控** | 监控基金在特定时间窗口（近 60 日/近 1 年/自加入观察日起）的自身回撤 | 记窗口期 $W$ 内最高复权净值为 $Peak_W = \max_{\tau \in W}(AdjNAV_\tau)$：<br>$$DD_{fund}(t) = \frac{Peak_W - AdjNAV_t}{Peak_W} \ge P\%$$ | 即使个人因为分批买入摊薄了成本（个人账面仅亏 $2\%$），但若基金自身较近半年高点已回撤达 $15\%$，及时提示标的本身已进入弱势区间 |
| **6. 触及/突破历史最大回撤监控** | 极值风险预警或左侧逆向布局（抄底/加仓）信号识别 | 记基金成立以来（或近 3 年/5 年）历史最大回撤为 $MDD_{hist}$，当当前本轮回撤 $DD_{current}(t)$ 满足：<br>$$DD_{current}(t) \ge \alpha \times MDD_{hist}$$ | 支持设置 $\alpha = 85\%\text{（临近极值预警）}$ 或 $\alpha = 100\%\text{（创历史最大回撤新低）}$；既可用于防范基金经理风格漂移导致的失控崩盘，也可用于宽基指数基金在触及历史极值回撤时提示左侧低吸 |
| **7. 单日/连续异动幅度监控** | 捕捉基金单日净值暴涨暴跌（如重仓板块突发利好/黑天鹅）或阴跌不止 | $$\|r_{day}(t)\| \ge W\% \quad \text{或} \quad \text{连续下跌交易日数} \ge D\text{ 天}$$ | 例如设定单日净值波动超过 $\pm 3.5\%$ 或连续 $5$ 个交易日净值下跌时发出异动提醒，辅助排查底层重仓股变化 |

#### 防骚扰与预警状态机（Alert State Machine）
当管理 30 只基金时，如果某只基金亏损 $-5.2\%$ 触发了“亏损 $5\%$ 提醒”，次日变为 $-5.3\%$，若每天重复推送相同消息会产生严重的通知疲劳。系统设计了三态防骚扰机制：
1. **首次触发（Triggered）**：净值跨越阈值的首个交易日晚间立即发送通知，并将该规则状态标记为`已触发待处理`。
2. **阶梯加深唤醒（Step Escalation）**：若用户未暂停该规则，仅当指标较上次触发点继续恶化超过阶梯步长（例如默认每加深 $2\%$：从 $-5\%$ 跌至 $-7\%$、$-9\%$）时，才再次发出升级提醒。
3. **自动复位（Auto-Reset）**：当净值反弹回到安全区（如回升至阈值上方缓冲带 $1\%$ 以上）或用户更新了持仓操作记录后，规则状态自动重置为`监控中（Armed）`。

## 3. 合规边界设计与多通道消息触达方案

### 3.1 面向公开上线的小工具合规风控设计
根据中国证监会《公开募集证券投资基金投资顾问业务管理规定》，未经许可的机构或个人不得向公众提供具体的基金买卖、清仓、减仓等投资建议。为了确保产品后续作为公开小工具上线时不触碰监管红线，产品在交互与文案层遵循**“纯工具属性 + 用户自设备注映射”**原则：

* **系统内置术语去投顾化**：系统界面与推送模板中完全不出现“建议清仓”、“建议减仓”、“建议止损卖出”等指令性词汇，统一使用“**移动回撤阈值触发**”、“**累计亏损阈值触发**”、“**历史最大回撤极值触发**”等客观统计描述。
* **支持用户自定义策略标签（User Tag）**：用户在创建规则时，可以自行填写最多 15 个字的“个人策略备忘标签”（例如用户自己输入备注：`执行纪律A` 或 `触发5%回撤线`）。推送通知时原样展示用户自己设定的标签与客观数据。
* **免责声明透出**：在小程序/网页底部及每次推送消息末尾固定附带简短说明：“*本工具仅基于公开历史净值及用户自行录入的数据提供客观指标计算与阈值通知，不构成任何投资建议。*”

### 3.2 消息推送文案标准模板示例

> **【基金策略指标触发通知】2026-10-19 盘后净值核算**
> * **触发标的**：华夏国证半导体芯片ETF联接C（008888）
> * **触发规则**：持仓最高盈利回撤 $\ge 5.00\%$（个人设定的策略标签：`回撤5%防守线`）
> * **当前净值**：$1.2350$（今日涨跌幅：$-2.45\%$）
> * **持仓表现**：当前持仓收益率 $+13.80\%$（持仓期间最高收益率 $+19.20\%$，较最高点已回撤 **$5.40\%$**）
> * **基金自身表现**：近 1 年回撤 $-14.20\%$（近 3 年历史最大回撤为 $-38.50\%$，当前处于历史回撤分位 $36.8\%$）

## 5. 核心数据库表结构设计（Supabase PostgreSQL Schema 蓝图）

以下 3 张核心业务表涵盖了“基金客观业绩”、“个人持仓动态水位线”与“复合监控规则”，可直接在 [Supabase](https://www.google.com/search?q=https%3A%2F%2Fsupabase.com%2F) 的 SQL Editor 中一键建表：

### 5.1 基金基础信息与客观业绩极值表（`funds`）
存储基金客观属性及每日盘后计算出的基金自身回撤指标（多用户共享，每只基金全库仅存一份）：

| 字段名 | 类型 | 必填 | 字段说明与计算逻辑 |
| :--- | :--- | :--- | :--- |
| `fund_code` | VARCHAR(10) | PK | 6 位公募基金代码（如 `008888`） |
| `fund_name` | VARCHAR(100) | 是 | 基金标准简称 |
| `fund_type` | VARCHAR(30) | 是 | 基金类型（股票型、混合型、债券型、指数型、QDII 等） |
| `latest_nav` | NUMERIC(10,4) | 是 | 最新官方单位净值 |
| `latest_acc_nav` | NUMERIC(10,4) | 是 | 最新官方累计净值 |
| `latest_adj_nav` | NUMERIC(12,4) | 是 | 最新复权单位净值（用于精确计算基金自身涨幅与回撤） |
| `nav_date` | DATE | 是 | 最新净值对应的交易日期 |
| `daily_return_pct` | NUMERIC(6,2) | 是 | 最新单日净值涨跌幅（$\%$） |
| `today_dividend_info` | VARCHAR(100) | 否 | 当日分红或份额折算信息（如 `每份派现金0.08元`，用于豁免除权日假回撤警报） |
| `consecutive_down_days` | INTEGER | 是 | 当前连续下跌交易日天数（上涨则归零，下跌则 $+1$） |
| `peak_adj_nav_1y` | NUMERIC(12,4) | 是 | 近 1 年最高复权单位净值 |
| `current_dd_1y_pct` | NUMERIC(6,2) | 是 | 当前较近 1 年高点的回撤比例（$\%$） |
| `hist_max_dd_pct` | NUMERIC(6,2) | 是 | 成立以来（或近 5 年）历史最大回撤比例 $MDD_{hist}$（$\%$） |
| `hist_peak_adj_nav` | NUMERIC(12,4) | 是 | 历史最高复权单位净值 |
| `current_hist_dd_pct` | NUMERIC(6,2) | 是 | 当前本轮较历史最高复权净值的回撤比例 $DD_{current}$（$\%$） |

### 5.2 用户持仓与动态水位线表（`user_positions`）
记录用户持有的每只基金份额、成本以及用于计算“最高盈利回撤”的动态水位线：

| 字段名 | 类型 | 必填 | 字段说明与计算逻辑 |
| :--- | :--- | :--- | :--- |
| `id` | BIGSERIAL | PK | 主键 ID |
| `user_id` | UUID | 是 | 关联 Supabase Auth 用户 ID（自用阶段可固定） |
| `fund_code` | VARCHAR(10) | FK | 关联基金代码 |
| `is_holding` | BOOLEAN | 是 | `True`=真实持仓基金，`False`=仅自选观察池基金 |
| `shares` | NUMERIC(14,2) | 是 | 当前持有份额 $S$ |
| `cost_unit` | NUMERIC(10,4) | 是 | 当前持仓成本单价 $Cost_{unit}$（由截图直接识别或手动录入） |
| `total_cost` | NUMERIC(14,2) | 是 | 持仓总成本本金 $C_{total} = S \times Cost_{unit}$ |
| `current_market_value` | NUMERIC(14,2) | 是 | 最新持仓市值 $M_t = S \times NAV_t$ |
| `current_profit` | NUMERIC(14,2) | 是 | 最新累计盈亏金额 $P_t = S \times (NAV_t - Cost_{unit})$ |
| `current_return_pct` | NUMERIC(8,2) | 是 | 最新持仓收益率 $R_t$（$\%$） |
| `hwm_nav` | NUMERIC(10,4) | 是 | **核心字段**：本轮持仓期最高单位净值水位线 $HWM_{nav}$ |
| `hwm_date` | DATE | 是 | 创下最高水位线的净值日期 |
| `hwm_return_pct` | NUMERIC(8,2) | 是 | 持仓期达到过的最高收益率 $HWM_{return}$（$\%$） |
| `drawdown_from_hwm_nav_pct` | NUMERIC(6,2) | 是 | 较最高净值水位线的相对回撤比例 $DD_{pos\_nav}$（$\%$） |
| `drawdown_from_hwm_ret_pct` | NUMERIC(6,2) | 是 | 较最高收益率回落的绝对百分点 $DD_{pos\_ret}$（$\%$） |
| `last_evaluated_nav_date` | DATE | 否 | 上次已完成策略扫描的净值日期（防止同一晚多次扫描重复触发） |

### 5.3 监控策略规则配置表（`alert_rules`）
支持全局默认规则（`fund_code = NULL`）与单只基金专属规则（`fund_code = 具体代码`）：

| 字段名 | 类型 | 必填 | 字段说明与计算逻辑 |
| :--- | :--- | :--- | :--- |
| `id` | BIGSERIAL | PK | 规则 ID |
| `user_id` | UUID | 是 | 所属用户 ID |
| `fund_code` | VARCHAR(10) | 否 | 为空代表全局默认策略，非空代表针对该基金的独立覆盖策略 |
| `rule_scope` | VARCHAR(20) | 是 | 监控维度：`POSITION`（个人持仓）、`FUND`（基金自身业绩）、`PORTFOLIO`（账户总组合） |
| `rule_type` | VARCHAR(40) | 是 | 枚举值：`TRAILING_STOP_NAV`、`TRAILING_STOP_RET`、`FIXED_TAKE_PROFIT`、`FIXED_STOP_LOSS`、`PORTFOLIO_DD`、`FUND_STAGE_DD`、`FUND_HIST_MDD`、`FUND_DAILY_VOL` |
| `activation_threshold` | NUMERIC(8,2) | 否 | 前置激活门槛（如最高收益率满 $10\%$ 后才开启回撤监控，默认 $0\%$） |
| `trigger_threshold` | NUMERIC(8,2) | 是 | 触发阈值（如回撤 $5.00\%$、亏损 $-5.00\%$、达到历史最大回撤的 $90\%$） |
| `step_escalation_pct` | NUMERIC(6,2) | 是 | 二次提醒阶梯步长（默认 $2.00\%$，防止每日重复推送） |
| `custom_label` | VARCHAR(50) | 否 | 用户自定义备注标签（如 `回撤5%防守线`、`触及历史极值定投区`） |
| `status` | VARCHAR(20) | 是 | 状态机：`ARMED`（监控中）、`TRIGGERED`（已触发处于冷却阶梯）、`PAUSED`（已暂停） |
| `last_triggered_value` | NUMERIC(8,2) | 否 | 上次触发时的指标数值（用于判断是否继续恶化达到阶梯步长） |
| `last_triggered_date` | DATE | 否 | 上次触发的净值日期 |

## 6. 方案整体复盘：6 个极易被忽视的隐蔽问题与工程兜底方案

在采用“方案三（Vercel + Supabase + GitHub Actions）”以及“公募基金双轨回撤监控”的实际落地过程中，有 6 个事先极易忽略但上线后一定会遇到的边界问题，已在方案中内置对应的解决机制：

| 隐蔽盲区问题 | 为什么会发生（触发场景） | 方案内置的工程解决机制 |
| :--- | :--- | :--- |
| **1. 老持仓首次录入时的“历史最高点（HWM）失忆”** | 假设某基金你已持有半年，上月最高涨过 $+25\%$（净值 $1.25$），今天跌到 $+18\%$（净值 $1.18$）。今天首次截图录入时，截图上只有当前净值 $1.18$ 和成本价 $1.00$，**没有历史最高净值 $1.25$**，直接按今日净值初始化 HWM 会漏掉已经发生的 $5.6\%$ 回撤 | **建仓区间历史最高值自动回溯**：在截图导入确认弹窗增加“回溯区间（默认回溯近 60 个交易日最高净值 / 自选建仓日期 / 以今日为准）”开关，系统自动从历史净值序列中提取该周期内的峰值作为初始 `hwm_nav`，也支持手动输入修正 |
| **2. 基金“现金分红/份额折算”引发的虚假暴跌警报** | 公募基金分红除权当日，官方**单位净值**会直接扣减分红额（例如每份分红 $0.10$ 元，单位净值从 $1.20$ 瞬间跌至 $1.10$，单日表观暴跌 $-8.3\%$），若直接按 `份额 × 单位净值` 计算持仓回撤，会立即误触发“回撤 $5\%$”或“亏损止损”警报 | **除权日自动识别与豁免提醒**：抓取天天基金 `pingzhongdata` 接口时同步解析 `unitMoney`（分红配送字段）；若检测到当日发生分红或拆分，**自动豁免当日的持仓回撤与止损触发**，改为推送一条“【分红除权校准提醒】请确认现金分红或红利再投后的新份额/成本” |
| **3. GitHub Actions 海外 IP 访问东方财富接口超时** | GitHub Actions 运行节点位于美国 Azure 机房，东方财富的部分动态行情 API（`push2.eastmoney.com`）对海外机房 IP 存在连接重置（Connection Reset）或限流策略，可能导致定时脚本偶发抓取失败 | **静态 CDN 接口优先 + 新浪财经双源降级**：主力抓取函数优先请求天天基金静态 CDN 脚本（`fund.eastmoney.com/pingzhongdata/{code}.js`，海外访问极快且稳定），同时内置新浪财经公开净值接口作为自动 Fallback 备用源 |
| **4. GitHub Actions 定时任务排队延迟与晚点基金漏抓** | GitHub Actions 的 Cron 在整点（如 21:00）排队严重，可能延迟 15～30 分钟执行；且不同公募基金净值公布时间跨度大（19:30 至 22:30 陆续公布，QDII 更是次日才出） | **非整点错峰双次调度 + `nav_date` 幂等锁**：将 Cron 设为北京时间交易日 **21:17**、**22:47** 及次日 **08:47** 运行三次；通过比对 `funds.nav_date > user_positions.last_evaluated_nav_date` 实现严格幂等——21:17 已更新并算过的基金，22:47 自动跳过；晚点出净值的基金由 22:47 和次日 08:47 自动补抓补推 |
| **5. Supabase 免费版“7 天无活动自动休眠”陷阱** | [Supabase](https://www.google.com/search?q=https%3A%2F%2Fsupabase.com%2F) 免费版规定：若数据库连续 7 天没有任何请求，项目会自动暂停休眠（Paused）。遇到国庆/春节长假连休 8～10 天不交易时，若脚本完全不跑数据库，节后首个交易日会因数据库休眠而报错 | **节假日保活心跳（Keep-Alive Ping）**：GitHub Actions 脚本每天照常启动，若通过交易日历判断当天为周末或法定节假日，虽不执行净值拉取，但固定向 Supabase 执行一条 `SELECT 1`（或更新 `system_heartbeat` 表时间戳），确保免费数据库全年 365 天永不休眠 |
| **6. Vercel 免费版 Serverless 接口超时与图片体积限制** | [Vercel](https://www.google.com/search?q=https%3A%2F%2Fvercel.com%2F) 免费版（Hobby）对 API 请求体大小（上限 4.5MB）和函数执行时长有限制；若用户一次上传 5 张手机原图（每张 5MB+）串行调大模型 OCR，会导致请求报错或超时 | **浏览器端 Canvas 预压缩 + 单张并发队列**：前端上传图片时自动在浏览器端将长截图等比压缩至宽 $1280\text{px}$、体积 $<500\text{KB}$，并由前端循环按单张图片并发调用 `/api/ocr-preview`（单张耗时仅 2～3 秒），彻底规避超时与体积限制 |

## 7. 核心交互页面规划（精简高效的 4 大核心视图）

为了避免做成臃肿的资讯软件，前端界面聚焦于“一眼看清 30 只基金的风险状态”：

1. **全景监控仪表盘（首页 Dashboard）**
   * **顶部汇总卡片**：展示总持仓市值、今日确认总盈亏、累计总盈亏、组合整体高点回撤比例，以及**“今日触发预警基金数（红色高亮 badge）”**与**“临近阈值观察基金数（黄色预警 badge，距离触发线不足 $1\%$）”**。
   * **多维排序持仓列表**：支持按“距离回撤触发线最近”、“持仓收益率”、“高点回撤幅度”、“离历史最大回撤距离”一键排序。每行同时展示两组进度条——左侧为“个人持仓盈亏与高点回撤条”，右侧为“基金自身本轮回撤占历史最大回撤比例条”。
2. **截图智能导入工作台（OCR Import Modal）**
   * 支持上传包含明确持仓明细（成本单价、持有份额/金额、持仓盈亏）的平台截图。
   * 解析完成后展示**校验预览表格**：若截图字段完整，则列出提取到的基金代码/名称、成本单价、份额、持仓金额与盈亏，并提供“初始最高水位线回溯周期（如近 60 日最高净值 / 今日净值）”选择；若某张截图缺失成本价或盈亏等关键字段，直接高亮报错**“未识别到完整有效信息”**并拦截，用户可选择更换详情页截图或手动填入。
3. **策略规则配置中心（Strategy Engine Config）**
   * **全局策略卡片**：例如一键开启“所有持仓基金：盈利后从最高点回撤 $\ge 5\%$ 提醒”、“所有持仓基金：累计亏损达 $-5\%$ 提醒”、“所有基金：本轮回撤达历史最大回撤 $90\%$ 提醒”。

4. **基金双轨详情与净值水位图（Dual-Track Detail View）**
